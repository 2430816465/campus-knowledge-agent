# 心动军师 AI — 产品需求与开发验收规范 PRD v1.0

版本：2026-10-12。状态：**五轮需求确认完毕；尚未批准开发**。本文件中的“目标”不等于已证实技术可实现。未经用户批准不得改变已决定需求。

## 1. 产品定位和原则
面向少数颜值聊天/陪伴型主播，在微信私聊中根据完整可用聊天历史、主播本人风格、观众独立档案提供多种候选回复；用户自主选择、修改、输入并发送。提高聊天自然度、开心程度、被重视感和沟通准确性，适当帮助延续话题。不可编造共同经历、感情承诺或利用脆弱性操纵观众；尊重明确拒绝和停止联系的要求。

## 2. 五轮锁定需求（不得擅自降级）

### 2.1 回复与分析
- 回复字数、标点、拆句/分条、错别字、语气词、emoji 完全以该主播经确认的真实聊天习惯为学习目标，不设固定范围；能够生成单条或多条消息组。
- 候选数量动态；综合排序：主播口吻匹配、聊天上下文、共情/快乐度、事实真实性、误会风险；可提示无需回复。
- 目标优先级：让对方开心(A)、感到被重视(C)、减少误解(D)；适当延续话题(B)而不强行留人。
- 暧昧/玩笑尺度基于真实交流、主播对每位观众的明确设置和边界，不擅自突破。
- 分析默认充分完成，界面先显示候选；点击可看完整军师报告：事实、假设、证据来源、不确定性、历史变化、候选理由、风险与下一步建议。
- 可根据用户需要提出新话题，也可不提出；生成仅在主播主动触发时发生。

### 2.2 全量历史、记忆、身份
- 每位观众当前不超过约1000条，但未来可增长；保存所有已成功取得的双向历史（含时间、顺序、发言人、媒介类型、来源与校对状态）。
- 模型上下文容纳时优先提供该联系人的完整可用文字历史；超出容量则分批通读、长期记忆、按原文回查；不可谎称处理了未读取消息。
- 多媒体：全量转写/描述可用于分析；相关时回调原图、语音和表情信息（若实际可获得）；未知不臆造。
- 初次导入以手机截图批量OCR、微信复制文字为主；电脑导入可选但不得依赖电脑保存完整历史。
- 新观众无标签也可回复；随聊天积累，AI提出标签，主播确认后生效；可手工添加/编辑；内部稳定联系人ID，昵称相同不得自动合并。
- 历史矛盾保留两条带时间的记录、优先较新可靠事实，有疑问提示主播；不得覆盖源记录。
- 学习全部主播本人历史发送文字为主，可选精选示例；结合后续实际发送内容持续调整，不能把AI候选误当成主播已发送文字。

### 2.3 微信接入与手机交互
- 首版优先Android，iPhone随后、Windows辅助；首批面向少数主播，用户数据完全隔离；首版单设备，未来可扩展跨端同步。
- Android：探索无障碍窗口内容+授权屏幕OCR+通知监听等合法可用信号；目标是自动收录微信全部历史和后续新消息，**包括无通知、未打开对话的消息**；要求**100%零遗漏**。当前不具备已证实的通用实现，必须先过P0技术闸门。
- 自动收录与主动生成分离：无论何时发现新消息，都不自动调用生成；主播点击才生成候选。
- 悬浮球+底部卡片+完整App三个界面；不自动填写或发送微信。主播自行选择、修改、打字发送。
- 尽可能识别自己实际发送的文字，可靠识别失败时人工确认。第一次批量截图导入需OCR去重、时间排序、说话人核对，低置信度强制校对。
- iPhone走复制文字、截图、系统分享/快捷指令入口，不承诺iOS后台自动读取微信。
- 图片、语音、表情、朋友圈截图/其他来源可由用户主动导入；不能读取时明确标注缺失。

### 2.4 AI组件
- 可选择不同生成模型，不强制对照模式；质量优先，允许较长响应时间。
- Jev支持开关/模式配置，**默认开启**；狗头军师和恋爱大师各支持开关，**默认两个都开启综合分析**。请先核对第三方Skill许可和适用范围；不能将Skill等同独立API或误把相对权重当心理概率。
- 生成模型负责最终撰写候选；Jev负责结构化判断辅助；两个Skill提供不同分析视角；融合前保留各自结论及分歧，避免无意义循环。
- 出现接口失败时明确报错，不静默关闭默认组件并冒称已完成全流程。可在用户主动确认后切换兼容模式。

### 2.5 费用与验收
- 典型使用每天10—30轮；月API费用期望30—100元，满100元提醒用户，经确认可继续；不得静默截断历史或关闭已确认开启的分析模块来省钱。
- 准备100组覆盖真实或授权/合成情境的测试，至少**95组满足事先定义的可用标准**；同时做匿名的普通LLM与完整系统对照实验（B+C）；对照测试用于判断组合增益，不额外强制其一定优于单模型。
- Android首版先保证指定的一台真机。用户自述设备“红米K80游戏版”，具体厂商型号/ROM和Android版本**尚待在设备设置页核对**，不要擅自映射到其他型号。

## 3. 关键冲突和未证实点
1. **P0绝对收录**：Android公开权限不保证读取微信无通知且未打开的内部消息；100%目标为硬性验收，不是已有能力。不得用“可见范围100%”偷换。
2. **完整既有历史**：微信若未暴露全部历史或历史已删除，截图/复制不能证明100%取得；应用需展示完整度核对状态和缺口，不能声称全量。
3. **100%准确识别与现实OCR**：跨消息类型、图片表情、折叠消息、引用、撤回及后台休眠几乎无法通过有限测试证明绝对零遗漏。必须明确消息全集的可验证真值来源；无真值源不能宣称100%。
4. **自动收录与不打开会话的矛盾**：不打开聊天时无法从视图树或屏幕读取消息正文，通知未产生则通知监听亦无数据。不能据此承诺后台全量。
5. **严格风格模仿与事实/边界**：严格模仿格式/口吻，不意味着模仿不安全/欺骗性内容；真实性和边界为限制条件。
6. **全量上下文与月预算**：每日10—30轮且频繁上传近1000条，真实费用依token长度、模型价格与缓存而变；先做计价实测。
7. **少数主播与首版单机**：多主播本机切换并隔离档案；跨设备同步暂缓。
8. **隐私暂不重点开发**：最小必要权限、本地加密/密钥安全、用户可删除、云端上传告知仍为基本技术底线，不可取消。

## 4. 架构建议（待技术闸门通过后执行）
原生Android Kotlin+Jetpack Compose；AccessibilityService（仅明确授权范围）、NotificationListener（只在授权时）、OCR服务（ML Kit/RapidOCR择优实测）、Room/SQLite数据库、WorkManager辅助状态修复（不得声称不被系统终止）、Android Keystore密钥；清晰界定UI层、会话采集适配层、去重层、联系人身份解析层、历史仓库、全量上下文组装层、模型适配层、Jev判断层、双Skill分析层、候选融合与事实核验层、计费层。禁止侵入/破解微信协议或数据库作为默认技术方案。

消息主键应综合本地稳定ID、联系人的独立ID、时间戳、发言人、内容哈希、来源证据；相同内容不必然同一消息。所有收录写入日志并记录来源、识别置信度、校对时间。对话切换立刻取消旧候选，避免跨联系人泄露。视觉截图中识别不到的内容标记“未知”。

模型全量上下文：清点本次可用消息全集及token数量；可完整装下时按时间顺序提供，含前后语境；超限先多批完成结构化事实抽取（事件、引用和时间轴），最后融合并支持逐条原文回查。输出结构化JSON并验证字段，保留本轮输入覆盖率、被省略内容及所用模型版本。每轮自动回归测试跨早期、中期、最新消息关键事实。

## 5. 分阶段工程计划（严格的停工闸门）
**G0 — 设备识别和基线**：核对红米设备确切型号、HyperOS/Android版本、微信版本、消息通知设置和备用测试账号。构建合成测试对话，准备可人工核对的真值清单；用户决定授权边界。

**G1 — P0最小验证程序（先于AI开发）**：仅实现可见消息视图树读取、授权截屏OCR、通知事件记录、会话识别、日志和去重。测试前台阅读、后台、锁屏、关闭通知、免打扰、完全未打开聊天、多位联系人同时发消息、连发、撤回、图片表情语音、断网重连、杀后台及系统重启等。对照独立真值清单，测查全量与遗漏。不得用手动补录填补自动识别的成功率；人工修复另行统计。G1不通过**停止正式产品开发**并向用户报告不能满足核心要求；只在用户另行明确改变硬性要求时才能换路线。

**G2 — 历史导入与账户隔离**：截图批量去重+文字批量导入、聊天双向身份校对、历史完整度审计、标签与手工备注、多人主播隔离、矛盾记录处理、媒体占位与来源追溯。

**G3 — AI核心**：多模型接口+可配置Jev默认开启+双Skill默认开启+原文上下文处理+结构化报告+动态候选+多条消息组+费用计量；模型失败/降级明确提示。

**G4 — 风格与UI**：从全部主播真实历史学习格式习惯；可选精选示例；点击生成、悬浮球、底部面板、完整详细报告、手动输入发送、实际发送反馈闭环。

**G5 — 真机稳定性**：长期连续运行、重启恢复、切换微信聊天、消息去重、ANR/崩溃、耗电、权限变化、离线恢复、多主播隔离、账单审计。

**G6 — 质量验收**：100组测试≥95组合格，匿名对照模型评分，所有P0硬指标独立通过，再发布安装包、完整源码、复现步骤、测试报告和已知限制。

## 6. 验收标准与测试集合
### 自动消息录入：硬门槛
定义基准集合G为真实到达指定微信账号的所有测试消息（含通知关闭/未打开）；A为程序在无需人工截图补录时保存且正文、联系人、方向、顺序均正确的集合。要求漏记数=0、串人=0、关键内容错误=0、重复展示=0。测试集至少覆盖上述G1场景，单独记录无通知/未打开场景。有限测试全绿仅代表指定样本，不得外推未来永远100%。缺乏系统外独立真值来源则判定“未能证明通过”。

### AI可用标准
每测试样本经主播盲评满足：①至少一条候选可直接使用或仅需轻微修改；②无编造共同经历/身份混淆；③充分利用关键历史；④语言形式贴近主播真实样本；⑤不会忽视明确边界。五条件同时成立才算该组可用。100组≥95合格；另分别统计早期历史回忆、图片语音准确性、暧昧边界、连发消息语境、无标签新观众。

### 对照试验
同一输入对普通LLM及完整架构各生成候选；隐藏方案来源，由主播按自然度、风格、历史贴合、情绪沟通与可用性盲评，报告偏好率和缺点，不凭“军师更复杂”宣称质量更高。

### 其他硬性要求
- 生成需要主播明确点击；无自动填框与自动发送。
- 切换联系人后旧任务结果不得显示到新联系人。
- 已发送学习必须参考实际确认文本而非未采纳草稿。
- 所有已确认启用组件实际运行或清楚显示错误；不得静默跳过。
- 100元月费提醒需用户确认继续；费用按真实服务计量并支持查看。
- 应用在未取到原始历史时明确标记“无法确认完整”，绝不虚称已有全部微信记录。

## 7. 仍待用户决策（不允许工程师自行拍板）
- 测试设备准确系统型号及微信版本（“红米K80游戏版”为用户口述，先核验）。
- P0验证时可否使用专门测试微信账号、辅助设备来核对真值；以及是否存在技术上可用、合规且用户明确授权的消息获取途径。
- “100%”是产品永恒保证还是只作为指定设备/测试场景的零遗漏验收？用户第五轮选C，本PRD按照最高硬要求保留，**尚不能承诺可达**。
- 报告中保存原始媒体的容量与保留期限；第一版媒体解析失败是否阻断全部功能，仍待确定。
- 用户是否要求生成候选时展示拼写/分段为可逐条复制的消息组，还是只需整段文本；当前确认不自动代发，默认可手动编辑。
- 最终使用的第三方Skill版本与许可边界，需实机开发前核查仓库最新状态。
